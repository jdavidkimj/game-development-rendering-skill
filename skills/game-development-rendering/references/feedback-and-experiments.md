# Feedback and experiments

Use the existing project learning system. Keep one canonical issue record, linked from the current resume, instead of duplicating evolving status across journals. Store private source and captures only in approved project locations.

Record the user's actual correction or approval, affected asset/version and visible target. Distinguish the user's words from the diagnosis. Reopen recurring issues and preserve rejected evidence. A new filename is not a new approach. Follow project retry limits; when repeated tweaks fail, obtain new causal evidence before continuing.

Choose an observable criterion and the cheapest evidence that resolves it. Trace the active asset, effective material and running version before repairing an unused copy. For shared assets, inspect a common reference and each affected integration route.

Keep implementation and verdict distinct: compiled, structurally verified, visually improved, published and user-accepted are different states. Silence is not approval. Praise of one exemplar does not prescribe its exact values for unrelated materials or anatomy.

Update the narrowest applicable record:

- Project or personal preference belongs in project memory/design rules.
- A measured technique or failure belongs with its project evidence and limitations.
- A transferable decision rule belongs in reusable guidance only within supported scope, with uncertainty and counterexamples retained.

Replace failed rules rather than accumulating reminders. Verify a method on a compatible second subject before broad expansion when compatibility is uncertain. Exact tolerances, asset names, private evidence and user-specific stage gates remain project-owned.

## Compact experiment fields

Use the project's format; a short entry can cover a local change. These fields guide useful evidence rather than mandate paperwork for every edit:

- **Target:** exact feedback, selected version/reference and later overrides.
- **Baseline/candidate:** source/asset/runtime identities, evidence locations, camera/settings and pose/time.
- **Hypothesis:** suspected cause, smallest useful change, expected result and disproof criterion.
- **Observation:** actual output or measurement, improvement/regression and remaining gap. State if no output was produced.
- **Verification:** relevant structural, still, motion, gameplay, lifecycle and performance checks completed or pending; user verdict/publication separately.
- **Lesson:** cause/confidence, decision changed, tested scope, uncertainty/counterexample and evidence for reuse.
- **Efficiency:** measured attempts/time/cost and avoidable rework; next smallest useful action. Do not invent savings.

Read only relevant open feedback and guides at startup. Reconcile results and rules at a useful batch boundary. Small validators can detect stale status or missing evidence but cannot establish visual quality. Durable records do not imply model training or background monitoring.

When changing this skill, validate packaging and replay realistic cases: an approved design, rejected construction, temporal claim, shared-asset mismatch and migration with reordered joints. Check whether the guidance preserves scope and chooses sufficient evidence. Independent evaluation can help when available and warranted; it is not required for every small edit.
